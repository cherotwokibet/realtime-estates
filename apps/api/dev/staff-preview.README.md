# Local synthetic staff preview

`startStaffPreview()` runs the actual API service, RS256 signature/claim verifier, ephemeral loopback JWKS and restricted nonowner PGlite transactions after both migrations. Independently authored fixtures contain no vendor exports, real properties, prospects, provider accounts or credentials. This is a development test harness, **not a login/session implementation**. It refuses `NODE_ENV=production`; both listeners bind only to `127.0.0.1`.

After building the domain and API, import it from a local development launcher:

```js
import { startStaffPreview } from './apps/api/dev/staff-preview.mjs';
const preview = await startStaffPreview({ tenantSlug: 'realtime-estates', port: 4101 });
// Hand preview.bearerToken directly to the Next development server's private
// STAFF_PREVIEW_TOKEN environment. Never print it or send it to the browser.
// Stop both loopback servers/database with: await preview.close();
```

The frozen result has `origin`, non-enumerable `bearerToken`, `listingId`, `revision`, `tenantSlug`, `expiresAt`, `acceptedMediaMetadataOnly`, `pendingReviewFixtures` and `close`. The default token identifies a synthetic assigned agent, expires after **30 minutes**, and is handed only to the calling process. There is no HTTP token/login/refresh endpoint, token file or token logging. Restart the launcher to create a new disposable database, key and token. Keep the token exclusively in server-side environment/configuration; no `NEXT_PUBLIC_*` variable or client component may receive it.

Trusted startup selects `realtime-estates` (default) or `sample-homes`. Default port is 4101; port 0 permits an ephemeral test port. No request query, header or JWT tenant/role claim chooses the company. Authenticated routes include GET/PUT `/v2/staff/listings/{uuid}/drafts/1`, POST its `/submit` suffix, admin GET `/v2/staff/reviews`, admin GET `/v2/staff/reviews/{uuid}/revisions/1` and admin POST its `/decision` suffix. Only the review queue accepts one bounded `limit` query. Public reads, enquiry writes, listing creation, media writes and membership administration are not exposed. Invalid methods, untrusted Host/absolute-form hosts, query context, cookie credentials and cross-origin requests fail. Server-to-server requests may omit Origin; a supplied Origin must match the API origin exactly. There are no browser CORS grants. The development bridge permits **128 KiB** only for exact v2 draft PUT routes and retains **64 KiB** for other routes. The API independently enforces its body limits, including **4 KiB** for submission and **8 KiB** for decisions, plus content/type/optimistic validation.

Realtime's draft ID is `00000000-0000-4000-8000-000000000400`; Sample Homes uses ending `500`. Each starts at revision 1, state `draft`, version **`"2"`**. Realtime's separate peer-assigned draft ends `401` and is inaccessible to the default agent. Base is KES 20,000/month, mandatory recurring service 1,000, refundable deposit 20,000 and one-off preparation 500: known recurring 21,000/month and known initial 41,500. Structured location is `Nairobi` / `Synthetic Nairobi town` / `Synthetic preview area`; coordinates are null and the private address is explicitly synthetic. A successful save returns the next version; use that version on subsequent saves/submission. Submission means **pending review**, never published.

By default the fixture explicitly seeds four accepted **synthetic media metadata rows**, with no image bytes, checksum verification, uploaded-file processing or owner/advertising-rights proof. Passing `seedAcceptedMedia:false` omits that fixture and submission must fail its actual SQL media gate. No upload endpoint or actual media processor is supplied. Connected UI must identify this local synthetic condition and must not advertise a verified real publication journey.

For an explicitly synthetic moderator session, trusted startup may pass `actor:'admin', seedPendingReviews:true`. The default main listing becomes pending revision 1, version `"3"`, listing version `"2"`, with fresh availability. A second pending listing ends `402` for Realtime or `502` for Sample Homes and is operationally paused, listing version `"3"`. Both companies receive separate fixtures to test isolation; only the configured company's queue is visible. Existing default draft fixtures are unchanged when the flag is false. Pending fixtures require `seedAcceptedMedia:true`; they do not add an accepted-media endpoint or verify any image bytes. Review detail returns accepted `{key,alt}` metadata references only, without signed media URLs or processor claims. Approval and rejection return revision version/state, and callers must reload authoritative detail. Approval preserves an explicit pause/archive; rejected corrections require a new revision. Publication status, availability and freshness remain separate from review state.

Tests may select synthetic `actor:'customer'`, `'revoked-agent'`, `'other-company-agent'` or `'other-company-admin'` at trusted startup to obtain genuinely signed tokens whose current database authorization must deny access. This is in-process fixture construction only; there is no browser-selectable identity switch. Normal editor launchers keep the default assigned agent; a separate synthetic moderator launcher explicitly selects the admin fixture.

Run `node --test apps/api/dev/staff-preview.test.mjs` from the repository root after building `@realtor/api`. Owned checks exercise real HTTP/JWKS, signature rejection, private draft reads, save/reload/conflict, current membership/assignment/company denial, metadata-dependent submission and admin queue/detail/decision readback. `node --test apps/api/tests/moderation.test.mjs` separately exercises actual restricted SQL approval/rejection, old snapshot retention, immutable pending/decided content, paused/archived approval, stale and superseded review conflicts, private reason exclusion and self-approval audit. They do not establish a deployed provider, MFA/session revocation, production PostgreSQL/PostGIS/pooling/TLS, real media handling, operator acceptance or real-device readiness.

## Synthetic viewing reply fault

`node scripts/enquiry-preview.mjs --web --invalid-first-viewing-reply` enables a process-only, one-shot invalid response after the first applied viewing request/proposal commits. It requires exact synthetic enquiry and catalogue modes; default behavior remains unchanged and production startup is refused. Denied/conflict/read responses never consume the fault. Original receipt reads and exact replay remain normal. No literal connection-loss or production fault-injection claim.

`node scripts/enquiry-preview.mjs --web --invalid-first-confirmation-reply` targets only the first applied phone confirmation;request/proposal/reads/denials/conflicts stay normal. Choose one viewing fault flag per launcher. The in-process value is `viewingReplyFault: invalid-first-confirmation-v1`;same production refusal and exact synthetic mode requirements apply.

## Explicit saved-reference moderation preview

Use `referenceModerationMode: 'synthetic-reference-transition-v1'` together with `referenceDraftMode: 'synthetic-reference-draft-v1'` in a disposable preview. This additionally installs the fourth reference SQL proposal only in its ephemeral database. Default migrations and ordinary previews do not install it. The mode requires synthetic accepted-media metadata and refuses native-upload combinations. The independently authored pending revision is submitted by the company's agent and can be reviewed by its different admin. Version 1 historical labels remain on that revision while version 2 is activated for new work.

For an isolated UI checkout with its own `.next` and dependencies, set `STAFF_PREVIEW_REFERENCE`, `STAFF_PREVIEW_REFERENCE_MODERATION`, `STAFF_PREVIEW_ACTOR=admin` and a separate `STAFF_PREVIEW_UI_PORT` before running `node scripts/staff-preview.mjs`. The launcher prints the exact `/reviews/{listingId}/1/references/4` page. Keep the ordinary port3001 and any occupied checkout untouched. API port is ephemeral; identity remains 30 minutes and server-only.

Optional `referenceModerationReplyFault: 'invalid-first-transition-v1'` (launcher environment `STAFF_PREVIEW_REFERENCE_MODERATION_REPLY_FAULT`) corrupts one successful transition response after commit. It never resends a transition and does not corrupt an original GET. Use this only to prove uncertainty and recovery. Unsupported/orphan modes fail before listeners. The metadata/health flags explicitly identify synthetic reference moderation; the token remains nonenumerable and is never logged or persisted.

These fixtures contain SQL-only accepted/sealed photo metadata, with no verified image bytes. The UI must show unavailable photos rather than inventing previews. Browser checks against this fixture cannot establish real media inspection, native processing, production login, hosted database races or operator acceptance.

## Explicit reference successor preview

Use `referenceSuccessorMode: 'synthetic-reference-successor-v1'` with the exact reference draft/moderation modes, or set `STAFF_PREVIEW_REFERENCE_SUCCESSOR=synthetic-reference-successor-v1` in an isolated UI checkout. This installs the successor SQL proposal only in the disposable database and seeds an approved primary reference revision per company. The launcher prints `/listings/{listingId}/successor`; no new listing ID is allocated. Ordinary previews/default migrations are unchanged. Public-preview combinations are refused. Optional `referenceSuccessorReplyFault: 'invalid-first-successor-v1'` / `STAFF_PREVIEW_REFERENCE_SUCCESSOR_REPLY_FAULT` corrupts one committed successful successor reply; original GET/refusal/denial do not consume it. Current bearer credentials remain server-only. See `docs/reference-successor-preview.md` for signed HTTP evidence and explicit browser/device/hosted limitations.
