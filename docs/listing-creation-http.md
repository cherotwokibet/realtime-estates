# Protected creation HTTP and SDK — synthetic verification

`/v2/staff/listings/{listing UUID}/creation-operations/{operation UUID}` accepts one POST with `{slug, content}` and GET for the exact immutable original. Route IDs own allocation/operation identity. The current authenticated staff subject and trusted deployment company own authority. Query context, cookies, caller identity/assignment headers, conditional requests, redundant idempotency headers, duplicate JSON keys, rounded money literals and unsupported fields are rejected. Both application and exact development-bridge POST bound the body at 128 KiB; unrelated routes retain their established limits.

POST normalizes a full private replacement before calling the atomic SQL function. The shared validator binds its returned receipt to the retained normalized command and verified actor inside the database transaction. A malformed adapter reply prevents commit; sanitised errors do not echo private content. GET calls only the original read function and validates actor plus route IDs. It never allocates a listing or adopts a current draft version. Both outcomes return 200: created or generic TARGET_UNAVAILABLE refusal. Later editing requires a fresh draft read.

SDK exports the shared immutable command/receipt validators and types. `createListingV2(command, staffOptions)` captures a detached normalized command, performs one POST and makes no hidden retry. `getListingCreationReceiptV2(retainedCommand, staffOptions)` performs only GET and compares the original facts. `getListingCreationSnapshotV2(listingId, operationId, staffOptions)` validates a historical original without asserting current editing authority. Applications must retain the validated command, IDs and uncertainty across their own operator state; browser retained-attempt/discard guards are not implemented by this SDK slice. Invalid successful write replies and network loss remain uncertain rather than becoming fresh allocations.

An actual loopback RS256/JWKS HTTP journey uses a restricted LOGIN / NOINHERIT / NOSUPERUSER / NOBYPASSRLS connection and trusted transaction context. It commits a creation, consumes its reply and deliberately throws in the SDK fetch adapter, then proves one original GET recovers it. Explicit same-command replay after later edits does not allocate again. Current assignment loss hides the original, restoration recovers it; another requester/admin cannot read it. Peer slug collision yields only a generic refusal. A separate injected wrong-actor SQL reply is rejected before transaction commit, leaving no listing/request; deliberate same-operation retry then succeeds. Final readback: two listings, three request/result pairs, five minimal audits (four create/save plus one later edit).
