# Release, rehearsal and rollback workflow

This is the documented workflow for the replacement; production deployment has not been completed. The canonical 97-task/14-gate checklist remains in the sibling realtor-delivery-dashboard. Task completion needs evidence for the whole deliverable; stage acceptance needs its tasks, dependencies and exit evidence. A partial code slice, green CI, Android export or published tracker cannot substitute for production/device/UAT/cutover evidence.

1. Inspect current source state and latest CONTINUATION.md. Choose a dependency-ready deliverable. Preserve vendor originals and the old live system. Use only synthetic fixtures while rights, access and data control remain unresolved.
2. Implement and review the exact source state. Run meaningful unit/contract/SQL/signed-HTTP/browser checks appropriate to the change. Run workspace typechecks and affected builds. Record real failures, limitations and unrun tests. Keep the KES 10,000 gross monthly baseline and service allowances explicit.
3. Commit/push to the controlled private Git repository, then restore a fresh clone and verify matching HEAD, clean checkout and git fsck --full. Record which commit was restored. This is source/history recovery; production database, media and signing-key recovery are separate rehearsals. A later publication-notes commit must also be backed up.
4. Check actual GitHub CI for the exact commit. The committed workflow installs the lockfile, runs tests/typechecks, builds web/admin and exports Android on Linux. Record run URL/status and warnings. No unrun/reused older result should be attributed to a newer commit. Formatting and workflow maintenance remain explicit work until configured and verified.
5. Before staging: verify provider/account control, reviewed deployment identity, managed secrets, supported API/database/transaction composition and a budgeted service plan. Apply reviewed migrations with a real production-capable runner and restricted runtime login. The disposable PGlite helper is not that runner. Do not provision paid services or buy credits to bypass a limit.
6. Rehearse a release in isolated staging with synthetic or explicitly authorized data. Verify current tenant/role/assignment denial, approved-public snapshot preservation, exact prices, media provenance, uncertain-operation recovery, real PostgreSQL concurrency, quotas/abuse controls, accessibility and supported browsers/native devices. Collect operator UAT and fix resulting defects. Record the exact source/config/schema versions.
7. Before any cutover: create authorized consistent database/media backups, verify independent restores, reconcile migration counts/relationships/media references, and rehearse rollback against disposable copies. Keep the prior source/config/schema and old service available. Define rollback triggers, decision owner and operator communications before changing traffic. Do not drop or rewrite live data as an improvised rollback.
8. Obtain Boniface's explicit cutover approval for the concrete verified release and traffic/account changes. Record approval and gate evidence. Switch only the approved resources; validate the live journey and monitor agreed service/operating-cost measures. If rollback triggers occur, use the rehearsed prior version and data strategy; record the decision and result. Decommission vendor/old services only after separately approved replacement verification and retention decisions.
9. Deliver source, account/access inventory, deployment/restore runbooks, operational guidance, known limitations and training evidence. Stabilization and handover remain open until verified and accepted. End the authorized continuation only after the complete rebuild/handover is achieved or Boniface cancels it.

For the private dashboard, export browser progress before editing its canonical plan; preserve every note and checklist/gate decision. Open the existing Sites source through its supported helper, preserve owner-only access, package the exact pushed dashboard commit and publish once. Import the merged canonical plan before reload, then verify the live checkpoint and exported progress. Store dated evidence and exact next steps. This dashboard workflow does not deploy the platform or alter the old live service.
