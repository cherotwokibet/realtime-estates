# Retained successor operator controller

Checkpoint 160, 24 October 2026. A framework-independent admin controller now retains an existing listing's reference-aware successor command before dispatch and restores it without network requests. BFF, screen wiring and actual browser successor testing remain pending.

`buildReferenceSuccessorCommand` adopts explicitly selected IDs and derives their public labels; it preserves the supplied existing listing, expected listing version, terminal predecessor and canonical private/pricing facts. It never infers IDs from legacy location text or allocates a new listing ID.

`referenceSuccessorSession` uses one storage key scoped to instance, tenant, verified actor and listing. A single bounded JSON entry contains that scope, full command and selected historical catalogue facts. Only the selected county/locality/neighbourhood ancestry and amenities are retained; unrelated catalogue entries are excluded. This keeps large catalogues out of recovery storage while preserving all facts required to validate the original snapshot. The selected subset is not new authority: SQL and the authenticated API remain responsible for current access and authoritative reference validation.

The 262144-byte storage bound is separate from the 131072-byte command/component and 262272-byte composed response bounds. Storage parsing rejects duplicate fields, noncanonical integer revisions, corrupt or misbound scope, unsupported fields and altered canonical envelopes. Selection/catalogue/content are validated and captured before writing. Quota failure or failed exact readback prevents dispatch. Capture makes semantic key order irrelevant to callers while the stored canonical bytes remain exact.

`prepareReferenceSuccessorAttempt` captures detached immutable facts, then synchronously retains and reads back the complete entry before one client POST. A second already-prepared controller cannot make a fresh submission while that original is retained. In-flight or uncertain states block discarding and departure; another command cannot replace the saved original. Storage altered during a write prevents confirmation and keeps uncertainty.

`restoreReferenceSuccessorAttempt` validates the stored command and selected historical catalogue locally. It calls neither catalogue GET, original GET nor POST automatically. Restored originals start uncertain. `recoverOriginal` and `replayOriginal` are explicit and must verify the same retained command/catalogue first. A denied or missing recovery result cannot silently clear an uncertain original. Known non-uncertain refusal can be explicitly discarded; late cancellation or malformed successful replies remain uncertain.

`verifyReload` permits only an uncertain, undiscarded original with exact retained bytes. It does not itself reload a browser or suppress a departure guard. The future UI must call it before an explicit full reload. A confirmed `freshDraftTarget` exposes only listing ID and allocated revision, never initial edit versions. The next screen must read fresh current draft/context before editing; original versions 2/3 do not authorize a later save. Explicit discard verifies storage clearing and readback. No automatic navigation or client requests are introduced by this controller.
