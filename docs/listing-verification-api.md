# Private synthetic verification API and history

The explicit `synthetic-check-record-v1` service option enables three current-admin routes: POST and GET `/v2/staff/listings/:listing/verification-operations/:operation`, and GET `/v2/staff/listings/:listing/verification-history?limit=N[&beforeVersion=V]`. Default service composition leaves these routes unavailable. Server identity determines tenant and actor; browser authority fields, cookies, conditional headers, ambiguous queries and malformed framing are rejected.

Commands retain the exact original target and independent history version. Shared strict record, receipt and history validators reject unknown fields, accessor inputs, unsafe or noncanonical versions, inconsistent actors, clocks, decisions and original facts. The API validates SQL projections before committing. POST dispatches once; a lost or unusable reply remains uncertain. GET original recovery performs no write and never silently resubmits. SDK reads bind the requested route and original facts but cannot replace server authorization.

Migration0031 adds descending keyset history using an optional exclusive `beforeVersion`. The response echoes that cursor and the current global history counter. A page remains bound to its older version window when newer records arrive; it does not claim the newest global head is unchanged. Limits remain1–25 with one-record lookahead. Current enabled-company/admin authorization remains mandatory on every page, including empty windows. The SQL function exposes no public table privileges.

Successful responses have bounded streamed JSON reads with fatal UTF-8 validation, exact declared lengths, duplicate decoded-key rejection and strict integer revision wire tokens. Request deadlines and cancellation include the response body. Notes and original facts stay out of recovery URLs. This remains synthetic staff assessment history; supported assessments confer no public badge or evidence authenticity claim.

The admin includes fixed dynamic same-origin adapters for those operation/history routes. They run only in the existing explicit loopback synthetic preview, use server-held credentials, reject browser identity and ambiguous framing, and validate the original route and response. Incoming command bodies are bounded to16KiB, use fatal UTF-8 and duplicate/revision-token checks, and share a30-second deadline with dispatch. Cancellation during an uncooperative body read returns without waiting indefinitely for stream cleanup. Empty chunks are discarded and periodically yield so an endless empty stream cannot grow retained memory or starve cancellation/deadline timers; that behavior has a regression test. Any failure after a write dispatch remains conservatively uncertain; recovery remains GET-only. No recording form or browser attempt state is implemented yet.

Verification evidence and final counts are recorded in CONTINUATION.md. The previous five-millisecond media deadline regression test expired before body reading under concurrent database load; its allowance is now250ms while retaining assertions for a started body read, cancellation and lock release. The failed log remains preserved. The first admin-boundary run used a bare403 mock instead of the SDK's required structured error envelope; it correctly became an invalid-response502. The fixture now uses the actual envelope without relaxing validation.

The initial admin production build compiled routes but stopped on the installed Next.js16.4.0 security advisory. Both web and admin were updated to16.4.2 with the lockfile, following the [official14October advisory](https://nextjs.org/blog/nextjs-security-update-october-14-2026). This does not establish that all mobile/transitive dependencies are free of advisories; the root audit is retained separately. Operator recording UI, signed HTTP preview, hosted concurrent PostgreSQL behavior, device checks, real evidence policy, production identity and cutover acceptance remain unfinished work.
