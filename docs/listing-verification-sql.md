# Private synthetic verification ledger

22 October 2026, checkpoint122. Default migration0030 implements the private synthetic policy from [listing-verification-policy.md](listing-verification-policy.md). It does not establish real verification or confer a public badge. Task06-6 remains open until the remaining application and acceptance work is verified.

Three private tables separate the per-listing history counter, immutable original operations/receipts and immutable assessment records. All force row-level security with owner-only policies; runtime and media-coordinator roles have no table access. API functions run as realtor_owner with a fixed pg_catalog search path; PUBLIC execute is revoked. The note validator and record projection helper have no runtime execute grant.

`record_synthetic_listing_verification` takes typed target/operation/currency/assessment/reference/note/observation parameters. It checks current active admin and enabled company before input or resource disclosure, then holds membership and company share locks through the transaction. A tenant/operation advisory lock serializes reuse even across different target listings, followed by listing, latest-revision and check-state row locks. Hosted multi-session lock/race behavior is not claimed from local PGlite tests.

Same-actor exact original replay returns its saved receipt after checking current access, even after later listing or history changes. Changed facts or another actor using that operation conflict rather than adopt its result. Target or history currency conflicts and future-observation/version-limit/regressing-record-clock refusals have stable original receipts but create no assessment record or check audit event. A successful record increments only the independent verification counter, appends its immutable actor/time/target/assessment snapshot and an attributable audit event, and stores its original receipt atomically. Audit metadata omits the private note and evidence reference. Listing content, revision content, availability confirmation, publication and approved snapshots are untouched.

`read_listing_verification(listing, operation)` is current-admin, current-company and original-requester scoped and performs no writes. `read_listing_verification_history(listing, limit)` is current-admin/current-company scoped, returns newest-first history with current counter, supports1–25 records and one-row lookahead with hasMore. It has no pagination cursor yet; do not present its first page as exhaustive history. Stored references are opaque synthetic identifiers, not validated evidence bytes or fetch instructions.

SQL and domain validation now agree on rejection of year0000 and C1 control characters. SQL explicitly uses the ECMAScript whitespace trim set for note boundaries so nonbreaking-space or BOM-wrapped text cannot bypass the shared validator. Notes remain bounded to600 Unicode scalars. Original canonical UTC millisecond observation text is validated before conversion. The recording clock comes from the server; no caller-supplied completion clock is accepted.

Focused tests cover restricted-role guarded synthetic seeds; shared-planner/SQL record parity; exact original replay/recovery after later history and a normal later availability change; changed facts/actor refusal; current nonadmin, cross-company, revoked membership and disabled-company denial; target/history conflicts; future observations; bounded ordered history; immutable records/operations; runtime table/helper denial; Unicode, reference and clock rejection; and atomic rollback on a deliberately injected audit-insertion failure. Maximum counter and future recording-clock boundaries use explicitly privileged fixture updates inside transactions that are rolled back, never retained fabricated history. Existing guards are not disabled.
