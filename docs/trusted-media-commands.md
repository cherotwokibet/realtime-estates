## Existing SQL boundary

Source paths are relative to `realtor-platform/`.

- `database/migrations/0001_foundation.sql:77`, `app_private.revision_media`: tenant/listing/revision composite FK; tenant/media UUID primary key; unique position per revision; positions 0–11; accepted boolean; key/type/byte/dimension/hash bounds. Neither key nor checksum is unique within a revision. These values are metadata, not evidence of actual decoding, distinct photos or advertising rights.
- `0001_foundation.sql:173`, `app_private.immutable_media()` / trigger `immutable_media`: locks the referenced revision and rejects changes outside draft. It does not check current actor/assignment, increment the revision version, manage output ownership or supply idempotency.
- `0001_foundation.sql:232`, `app_private.lock_listing()`: current tenant, listing lock and current `may_work()` assignment/admin authorization. `app_private.staff_role()` checks active membership and enabled company. `require_version()` requires a version but media commands do not exist yet.
- `0001_foundation.sql:153`, `touch_version()` / `touch_revision`: one revision UPDATE increments its token. No existing media trigger performs that UPDATE.
- `0001_foundation.sql:292`, `app_api.submit_revision()`: listing then revision locks, exact revision version, draft state and count of 4–12 accepted rows. It currently counts rows, including duplicate keys/hashes, and has no verified-job provenance gate.
- `0001_foundation.sql:316`, `app_api.decide_revision()`: listing then revision locks, admin-only exact pending decision, photo reference snapshot ordered by position. `public_snapshots.photo_refs` is JSON, not an object-lifetime FK. `0002_listing_disclosure.sql:92`, `copy_snapshot_disclosure()`, copies exact approved pricing/location; it supplies no media job provenance or cleanup protection.
- `0001_foundation.sql:212–219`: `api_runtime` has scoped SELECT on media and no arbitrary media DML. Keep that boundary. `apps/api/src/database.ts`, `assertSafeRuntimeConnection()`, intentionally permits only the existing isolated API login/role; do not weaken it to accommodate a worker.

## Minimum scope and proposed roles

Implement single-photo processing and explicit single-photo attachment first. The UI attaches one output, reads the resulting draft/version, then starts the next attachment. No bulk attach or automatic adoption of a newer version. Multiple temporary jobs may finish, but attachment is still version-controlled: two attachments using token N cannot both succeed.

The processor decodes/re-encodes actual bounded bytes in an isolated worker. It has **no browser token, arbitrary database DML, API-role membership or ability to select an acting user**. A trusted coordinator issues a short leased job and receives verified output facts through a private channel. Coordinator and lease trust are new implementation requirements, not existing evidence.

Proposed dedicated `media_coordinator` NOLOGIN, NOINHERIT, NOSUPERUSER, NOBYPASSRLS role; its isolated login has only that role. Grant USAGE on a new private `app_media` schema and EXECUTE on named job/seal/finalize functions only. No table DML, `api_runtime`, `realtor_owner` membership, owner credentials or arbitrary SQL interface. Functions are explicitly owned by the controlled migration owner, SECURITY DEFINER, fixed `search_path=pg_catalog`, schema-qualified and revoked from PUBLIC. Do not repeat a broad `GRANT EXECUTE ON ALL FUNCTIONS` for the new schema. A separate coordinator connection guard must prove this precise permission set; the ordinary API connection guard remains unchanged.

`api_runtime` receives only narrow authenticated registration, attach-intent creation, receipt-read, remove and reorder commands. Authenticated HTTP supplies identity from the verified server context; no tenant, actor, role, storage key, hash, dimensions, accepted flag or manifest is accepted from a browser body. Coordinator finalization derives business context solely from the persisted authenticated intent/requester and rechecks authorization; caller-selected GUC values cannot choose another actor. The SQL role/context boundary itself is not JWT verification.

## Job, object and operation records

Proposed private upload jobs have immutable UUID, tenant/listing/revision tuple, requester, assigned agent at registration, generated quarantine/output identifiers, captured input generation/hash, pipeline version, expiry and state. Use composite FKs. Quarantine is separate from `revision_media`; an unprocessed upload never occupies an accepted photo position.

Proposed states: `registered -> processing -> verified -> attached`; explicit `failed/cancelled/expired` branches. A processing claim is a short transaction issuing an opaque lease nonce, expiry and attempt number. Never hold a database transaction open during upload/decoding. A stale worker cannot seal output under an expired/replaced lease. Seal the input generation/checksum once; reusable presigned upload locations must not permit a subsequent overwrite to silently change the captured processing input. A verified manifest is immutable, including output checksum/bytes/dimensions/type, actual captured input digest and pipeline version. The generated immutable output key is derived from the registered tuple/job, not supplied by a client. Rewriting an existing output key with different bytes fails.

The coordinator seals verified facts through a narrow proposed `app_media.record_verified_output(job_id, lease, manifest)` command. This is an internal trusted attestation boundary: SQL constraints cannot prove that a decoder ran. The processor/coordinator and byte-level tests must establish that separately.

Keep **upload registration identity and attachment operation identity distinct**. A tenant-scoped `registration_id` idempotently creates one upload job and returns a registration receipt; it does not authorize attachment. Use one tenant-scoped operation UUID namespace across command kinds, so repurposing a registration UUID as an attachment is a kind/payload conflict. The job UUID is a separate resource identity. The registration's canonical request binds requester, tuple, job ID, initial draft version and validated alt text. The receipt records job identity, not a renewable upload capability. Issuing any fresh upload capability requires separate current authorization and permissible job/draft state; replaying a receipt cannot reopen a submitted/cancelled job.

After a job is verified, an authenticated current user creates a separate `attach_operation_id` through `create_media_attach_intent()` below. The immutable intent binds actor, tenant/listing/revision, verified job ID, **the version explicitly supplied by that user**, validated alt text and sealed manifest digest. The coordinator consumes that exact intent; it cannot manufacture an actor, choose/adopt a newer version or relabel a worker claim as another user's operation. Processing-job leases and attachment operations are different identities. Reusing verified bytes does not transfer an old lease or alter the sealed job.

Persist the tenant-scoped operation UUID, initiating actor, command kind, canonical request payload, server-computed digest and lifecycle/outcome. Compare canonical payload as well as digest; a caller cannot choose a digest to bless changed input. Remove binds media ID; reorder binds the complete ordered ID array. Same operation with changed version, body, principal or output conflicts, including after a conflict outcome. The intent-creation acknowledgement is **not an applied-media receipt**: an intent may be ready, then finish applied/conflict/rejected/expired. Once the terminal mutation outcome/receipt commits, it is immutable. An identical creation retry returns the existing intent status or committed terminal receipt without creating/reapplying work. Operation receipts survive temporary-job cleanup according to the eventual retention policy.

Every new HTTP revision-version field must use the moderation-style **original raw positive integer token check before JSON.parse**, followed by a safe supported integer range check. Reject fractional/exponent literals that could round into integers, including escaped version-field names. Reject duplicate decoded object keys, including escaped duplicates. `Number.isSafeInteger()` or SQL bigint coercion alone is insufficient. These are future media HTTP boundary requirements; no executable API changes are included in this draft.

## Proposed commands and locking

Only command1 and its narrow readbacks exist. Commands2 onward remain proposed.

1. Implemented `app_api.register_media_upload(listing_id uuid, revision integer, expected bigint, registration_id uuid, alt_text text)` — active assigned agent/admin only. Listing/revision locks and tenant operation serialization precede server job UUID allocation. New registrations require current draft/exact version; matching historical replay recovers the original result under current authorization after later state/token/expiry changes. Generated private storage identities allocate no objects. There is **no attachment intent** and no revision increment. Alt text is canonical, nonblank, control-free 1–300 Unicode code points. Narrow `read_media_registration(uuid)` and `read_media_job(uuid)` omit private storage facts. Registration UUID cannot be repurposed under another command kind.
2. `app_api.create_media_attach_intent(job_id uuid, expected bigint, attach_operation_id uuid)` — `api_runtime`, active authenticated assigned agent/admin. The trusted server context supplies the current user/company. Resolve the job's immutable tuple, lock/recheck listing and revision, and require current draft/exact user-supplied version, enabled tenant, same original requester, current authorization/registered assigned agent and a sealed unexpired verified job not already attached/cancelled. Persist the immutable intent described above, with the manifest digest and captured validated alt text from that job. This command creates no media row and does not increment the revision token. Its acknowledgement means attachment is queued, not accepted/published. An identical retry reads its existing status/terminal receipt under current read authorization; a different expected version under the same UUID conflicts. After a stale attempt, **this is the only command that can authorize a fresh attachment operation with the same verified job and a NEW UUID/version**. Cross-user transfer is deferred.
3. `app_media.finalize_media(attach_operation_id uuid)` — coordinator-only. It accepts **no fresh job, version, actor, tenant or manifest argument**. Resolve the persisted authenticated intent and its sealed job; derive all business context and expected version from those records, not caller-selected GUC values. Recheck the stored actor's active membership, enabled tenant, current assignment/admin authorization and registered assigned agent. Require draft/exact intent version, unchanged manifest digest and still-valid verified job for a new mutation. Append at current row count, enforce capacity <=12, attach accepted verified metadata, mark job attached and commit the intent outcome atomically. An already committed identical intent replays its historical receipt subject to the authorization rule below. Coordinator consumption cannot auto-refresh an intent or manufacture a new one. A failed/stale attempt preserves reusable verified bytes but cannot silently become another operation.
4. `app_api.remove_draft_media(listing_id uuid, revision integer, expected bigint, operation_id uuid, media_id uuid)` — current assigned agent/admin, exact draft version and exact tenant/revision media ID. Remove the association and compact remaining positions. This is not immediate object deletion. New operations targeting absent media fail; retrying a previously successful identical operation returns its receipt.
5. `app_api.reorder_draft_media(listing_id uuid, revision integer, expected bigint, operation_id uuid, ordered_ids uuid[])` — current assigned agent/admin, exact draft version. Require a non-null dense array containing every current media ID exactly once, no extras/duplicates/foreign IDs, max12. At the SQL boundary allow the canonical empty array, otherwise require one dimension, lower bound 1 and no NULL entries. Apply order atomically. New-path quarantine jobs are not media rows. Legacy unaccepted rows need an explicit migration/read policy; do not silently omit them from full-set validation.

All new mutations acquire **listing -> revision -> operation/job -> media** locks in a consistent order. Job tuple lookup before locks is read-only and must be rechecked under its row lock. Resolve authorization before exposing historical receipts. `immutable_media()` remains a defense in depth, not the authorization mechanism. Serialization uses the same listing/revision locks already held by save, submit, withdraw, reassignment and decision.

Every actual attachment/removal/order change performs exactly one revision UPDATE, letting existing `touch_revision` increment the revision token once, then audits the resulting version through `app_private.audit()` and stores its receipt in that same transaction. Media-only changes do not increment the separate listing token. A new reorder already equal to the current order may be an explicit `noop` receipt with unchanged token; it still validates authorization, draft/current expected token and full set. Other no-op behavior must not be invented implicitly.

Current position uniqueness is immediate and positions are constrained to 0–11; a swap/compaction cannot safely rely on transient duplicate or negative positions. A future migration should explicitly name a DEFERRABLE position uniqueness constraint, defer only it within reorder/remove, and prove the final contiguous 0..N-1 set before returning. Preserve the range check. Do not use a dummy position outside the permitted range or disable the immutability trigger.

Reject duplicate verified output checksums **or** generated output keys within the same draft, including outputs whose different source files re-encode to identical bytes. Enforce database uniqueness as well as command checks so competing operations cannot each attach the same output. No perceptual-duplicate claim: different encodings/near-identical photographs require a separately defined policy. A later revision may legitimately reference an earlier immutable object through an explicitly authorized carry-forward flow; that flow is not supplied by current `save_draft_v2()` and is outside the first single-photo slice.

## Receipts, conflicts and races

A successful receipt records operation kind/UUID, listing/revision, resulting revision version, media ID/order and applied/noop outcome. It is a historical result, not current draft state. Receipt replay/reconciliation requires current tenant/read authorization and the same principal/canonical request. It must **not** require the old version still be current, the revision still be draft, the worker lease still be live or the attached row still be present. It performs no media mutation, version increment or duplicate audit. This permits recovery after a lost response followed by save, submit or later removal. Revoked, reassigned-away or other-company users cannot recover private receipts through guessed UUIDs.

For a new attachment, an intervening content/media change makes the intent's expected token stale: conflict, no media/version change. Keep the verified temporary output private and reusable until expiry. After explicit readback, the same authorized actor may invoke `create_media_attach_intent()` with a **new attachment operation UUID**, the new exact version and the same verified job; no reupload is needed. Reusing the old attachment UUID with a newer version is a changed request and conflicts, even if the old outcome was a conflict. Reusing the registration UUID does not create an attachment. Neither the coordinator nor a processing worker can perform this user authorization step or silently retry against the latest version. Persist bounded terminal conflict/error information without turning an uncommitted attachment into a success.

Persist expected stale/state conflicts as bounded typed outcomes on the committed intent while holding the normal locks: mark it conflict/rejected, leave media, revision token and success receipt/audit unchanged, and return without RAISE so the outcome commits. If an exception aborts the transaction, a separate narrow compare-and-set may record failure only after confirmed rollback, matching the intent and attempt/fencing token and only while nonterminal with no success receipt. Never overwrite a terminal outcome or infer failure from a timeout with unknown commit status. Authorized reconciliation must expose the stale intent as a durable conflict, while keeping its verified output private and reusable through an explicitly authorized fresh intent.

If finalize wins the revision lock, it attaches and increments N -> N+1; a submit carrying N conflicts. A submit using the fresh N+1 can then review the exact media set. If submit wins, state becomes pending and any new finalize/remove/reorder rejects; verified temporary output stays private for reconciliation/expiry. Decision acts only on pending media and snapshots it atomically. Neither a new upload nor draft removal/reorder may alter an old approved snapshot. Aborted media transactions must roll back media, token, success receipt and success audit together; a separately committed bounded failure outcome follows the rule above.

## Publication and cleanup gaps to close

`submit_revision()` currently counts accepted rows. A verified-media journey needs 4–12 distinct accepted outputs with sealed job provenance, not merely four fixture rows; plan that migration and intentional fixture updates explicitly. Do not label existing metadata-only fixtures decoded or verified during backfill. Metadata-only SQL authorization tests remain distinct from actual-byte pipeline tests.

Verified draft output stays private. Delivery resolves only the current permitted approved snapshot, with no arbitrary-key proxy. Removal creates a cleanup candidate; a sweeper deletes only unreferenced objects after the retention/grace policy and rechecks references under a safe protocol. Retained revision rows, `public_snapshots.photo_refs`, operation/job recovery and backups all matter. An old approved revision may still reference a key even after a later public snapshot replaces it. Preserve those references; a simple count of current draft rows is insufficient. Paused/archived snapshots remain retained privately. Storage failure before commit leaves private cleanup work; storage deletion is never part of the attachment transaction.
