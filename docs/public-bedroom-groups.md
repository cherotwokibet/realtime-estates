# Explicit bedroom search groups

Checkpoint 187, 25 October 2026. [Business rules](business-rules.md) and [AC-014](acceptance-catalogue.md) distinguish exact stored bedroom counts from a “7+” search group. This change implements the shared public API/SDK contract; complete browser, device and release acceptance remains separate. KES 10,000 remains the total recurring service-price baseline per realtor.

Both `/v2/properties/search` and the explicitly gated synthetic `/v3/properties/search` accept optional `bedsMode=at_least` with the existing `beds` parameter. The mode uses the fixed SQL comparison `bedrooms >= bound`. An absent or blank mode preserves `bedrooms = bound`, including exact 7, 8, 9, 10 and studio 0. Thus “7+” is represented by `beds=7&bedsMode=at_least` and includes exact 7. It never rewrites stored counts or makes an existing `beds=7` URL grouped.

Mode tokens are exact: case changes, whitespace, unsupported modes such as `over` or `exact`, and repeated mode keys are rejected, including repeated blank or identical values. The explicit mode requires a supplied nonblank canonical count. Counts remain decimal integers from 0 through the existing defensive maximum 100; padded, signed, fractional, exponent and literal `7+` values are invalid. API and SDK retain the same bound. Blank mode with no count remains unrestricted. A SQL null count does not match either numeric comparison, including `>= 0`; unknown or not-applicable never becomes studio 0. Private and shared bathroom filters keep their separate existing comparisons and exclude null counts.

The SDK exposes `readonly bedsMode?: 'at_least'` on `PublicSearchInput`. Both versions share input snapshot and validation before transport, reject accessors without invoking them, retain count/mode/pagination independently of later caller mutation, and omit runtime blank mode from the outgoing query. Existing anonymity, credentials, company authority, reference gate, retry behavior, stable ordering, SQL/response bounds and one-statement count/page snapshot semantics are unchanged. No schema, migration or default activation is added. Grouped bedrooms combine with the existing purpose, type, location, bathroom and exact-price predicates using logical AND, including strict Over from checkpoint 186.

Parser/SDK regressions cover both search versions, exact counts and blank/default compatibility, an explicit inclusive group, defensive boundaries, malformed/repeated mode and count inputs, missing count, getter refusal, no-I/O validation and paged wire snapshots. The existing actual restricted-role 102-record embedded PGlite scenario reuses six existing stock records for 6, 7, 8, 9, 10 and null-land bedroom facts. Their IDs, titles and exact prices are preserved, so its original total, ordering, paging and checkpoint-186 price assertions remain unchanged. Its former 101 studio records in Synthetic Town become 95 because those six records now carry the explicit boundary facts. A foreign-company 7-bedroom record verifies grouped isolation without changing either company's total stock.

The expanded SQL scenario must find all four 7-through-10 records over two pages with exact total four and no duplicates, preserve each exact count, exclude the 6-bedroom and null-land records, retain studio 0, and keep null out of an at-least-zero query. Composed price/type/private-bath filters must select the expected two records. Separate private/shared numeric bathroom filters must exclude their respective null facts; the fixture now has two known shared-bathroom counts, so its numeric shared-bathroom query expects two rather than the former zero. All original price, privacy and unrelated query assertions remain. Its sealed media metadata is SQL-only fixture data, not image processing, provider or hosted PostgreSQL proof.

The demo and public website expose Exactly and At least comparisons, preserve the selected mode in chips, paging URLs and form state, and retain unsupported raw mode selections for correction. Existing web/demo count-text trimming remains; the canonical count-token refusal described above applies to API/SDK inputs. Invalid queries do not broaden into unfiltered results.
