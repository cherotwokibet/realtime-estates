# Strict Over for public base-price search

Checkpoint 186, 25 October 2026. AC-009 requires an explicit strict “Over” option in addition to the inclusive minimum introduced at checkpoint 184. This implements its shared API/SDK contract. Complete application, browser and release acceptance remains separate. KES 10,000 remains the total recurring service-price baseline per realtor.

Both `/v2/properties/search` and the explicitly gated synthetic `/v3/properties/search` use the same parser. Optional `minMode=over` changes only the minimum comparison from `amount_minor >= bound` to `amount_minor > bound`. An absent or blank mode retains the inclusive comparison. Unknown values, different casing, whitespace and repeated mode keys are rejected, including repeated blank or identical values. `over` requires a supplied positive `min`; omitting it or supplying a blank minimum is invalid even when a maximum exists.

The existing exact KES conversion and explicit price basis still apply: choose sale, or rent with a rental period. Zero, negative, exponent, nonnumeric, overprecise and unsafe amounts fail closed. The lower threshold is bound as its original exact integer minor-unit value with a bigint cast. The fixed SQL operator handles strictness without adding a cent to the input, including at the largest safe amount. The maximum stays inclusive. A minimum above the maximum is invalid; equal bounds with `over` are valid and return an empty result because no amount can satisfy both predicates.

The SDK exposes `readonly minMode?: 'over'` on `PublicSearchInput`. Both search methods share its strict input snapshot, reject accessors and malformed mode values before transport, retain exact decimal strings, and send one anonymous GET. Runtime blank mode remains compatible and is omitted from the outgoing query. Existing credentials, authority, tenant selection, context, retry, response framing, count/page snapshot, sorting, statement timeout and response-size rules are unchanged. No migration, schema or default reference activation is introduced. Prices continue to mean base price; deposits, fees and unresolved charges keep their separate disclosures.

Parser and SDK regressions cover both versions, blank/default inclusive behavior, exact strict SQL and wire bounds, sale/rent basis, equal upper-bound composition, the safe amount ceiling, malformed/repeated/missing-minimum modes, no-I/O rejection, accessor refusal and input mutation after dispatch. The existing 102-record restricted-role embedded PGlite SQL fixture was expanded rather than duplicated. Its strict KES 20,000.00 case excluded the exactly equal original record and started with the KES 20,000.01 record; strict KES 20,000.01 composed with maximum KES 20,000.02 returned just the one-cent-higher record. Equal strict bounds returned zero with an empty page, while blank mode preserved inclusive equality. Existing foreign-company, privacy, paging and exact-count assertions remain in the same scenario. Its media provenance is SQL-only fixture data, not proof of image processing or providers.

The demo helper, bounded web catalogue and global web search preserve the explicit comparison independently of the amount. The form offers “At least” and “Over (excludes equal price)”; its chips and help use the selected meaning. Paging links and the form remount key carry `minMode`. Unsupported raw selections remain visible for correction and return validation errors with no broadened search. A read-only review caught whitespace normalization initially accepting padded mode tokens in the demo/web layer; those layers now also require exact empty or `over` tokens. The existing company-wide option recovery read remains separate from a refused search.
