# Atomic listing creation — local synthetic SQL

Migration 0022 adds `app_api.create_listing_draft_v2(listing UUID, operation UUID, slug, normalized content)` and `app_api.read_listing_creation(listing UUID, operation UUID)`. The server derives company, creator and self-assignment from current verified staff context. Agents and admins may create; callers cannot supply company, actor, assignee, media or publication authority.

A private append-only request reserves each company/operation identity before the listing exists. Its deferred foreign key requires a completed result before commit; the completed result also references that exact request/target. A successful subtransaction allocates the listing and initial draft together, using the established create/save guards and minimal audits. Only the two expected listing UUID/slug uniqueness constraints become durable generic TARGET_UNAVAILABLE refusals. Other errors roll back the whole operation. There is no committed pending state.

Repeated operations must have the same target, original requester and exact normalized slug/content. Changed retained facts conflict rather than becoming a new allocation. Reads and replay check current staff membership; successful originals also require current access to the created listing. A later draft edit never changes the original receipt or turns its initial versions into current editing authority. Refusals include only the caller's request and generic reason, not the conflicting listing or agent. An admin cannot recover another requester's original merely by having company-wide listing access.

Both ledgers force row-level security, expose no runtime direct reads/writes and reject update/delete even under the owning role. Existing trusted bootstrap create/save functions remain available: this slice does not yet enforce exclusive creation through the new operation. HTTP zero-version allocation transition must be decided and tested before any exclusivity claim.

The new private content predicate accepts exactly the 18 full replacement fields, explicit defaults/nulls, bounded canonical base text, exact money/counts, paired coordinates, property/room consistency and existing pricing/location checks. It runs before reservation or collision refusal. It preserves original private address whitespace while rejecting forbidden controls. It complements domain normalization and retains existing SQL pricing total restrictions; it is not a claim that every partial domain input is already a normalized database snapshot.

Private snapshots include address and draft facts to validate/recover an exact retained request. Content has field/charge bounds and is excluded from audit summaries, public pages and dashboard notes. Disposable synthetic test databases are closed after checks. No production snapshot retention/deletion/archive policy or cleanup service is implemented; production use requires explicit rights, retention and recovery decisions. Immutable storage must not be represented as an implemented timed deletion policy.

Focused restricted-role PGlite checks cover created domain-compatible originals, historical replay after later edits, changed request conflict, wrong requester/route/company denial, assignment and membership loss/restoration, generic collisions, invalid snapshots before refusal, outer rollback, deferred orphan failure, forced RLS/immutability, Unicode/exact money and independent company/admin creation.
