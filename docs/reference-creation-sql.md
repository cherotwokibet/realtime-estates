# Atomic reference-aware creation candidate

Checkpoint 150, 24 October 2026. Isolated synthetic SQL only; not registered in default migrations, API routes, SDK or UI.

The fifth candidate, `database/proposals/listing-reference-creation.sql`, loads after the existing draft, catalogue-install, read and moderation proposals. It composes the existing guarded v2 creation function and combined reference save inside one database transaction. A fresh successful operation allocates one assigned draft, saves normalized content, adopts the selected current catalogue and records an immutable composed original. Invalid references or disclosure roll the allocation and every associated receipt back together.

`app_api.create_synthetic_reference_listing(uuid,uuid,text,jsonb,jsonb)` receives listing ID, operation ID, slug, private content and reference selection. Authority remains the verified transaction's current tenant/actor; no assignment, reviewer, media acceptance or publication authority comes from this payload. A fresh creation's immutable v2 subreceipt records initial editorial version 2. Its reference subreceipt records adopted version 3. Neither original is a statement about the draft's later editable version.

A target-ID or slug collision raises `40001` and aborts the entire composed command, including the nested v2 refusal receipt. The new contract does not claim a durable refusal without retaining the complete reference selection. Other unexpected errors are not caught or turned into success. New selection validation, parentage, compatible amenities, public labels and current-pointer locking reuse the existing reference save.

The private completed-receipt table has a tenant/operation primary key, foreign keys to both underlying originals, forced row-level security, owner-only policy, immutable update/delete trigger, and no runtime table privileges. The existing guarded creation reservation serializes matching SQL operations. Successful matching replay returns the stored composed original after current role/requester/assignment checks, even after catalogue activation or later edits. Changed content, slug or selection cannot replace it. A current customer, revoked member, other requester, reassigned agent or other company cannot recover its private facts.

`app_api.read_synthetic_reference_creation(uuid,uuid)` observes only a retained composed receipt after the original creation read's current authorization. Merely creating v2 stock and saving references independently cannot fabricate this recovery result. An explicit composed write may reuse fully matching underlying originals; it must pass both original binders and retain its own marker. This compatibility behavior does not prove those earlier independent operations happened atomically. Fresh operations are the atomic-allocation path verified here.
