# Explicit synthetic catalogue activation candidate

Checkpoint130, 23 October 2026. The isolated persistence proposal now uses a saved catalogue manifest and a separate current-version pointer. `database/proposals/listing-reference-catalogue-install.sql` loads after `listing-reference-draft.sql`; neither file belongs to the default migrations or an application route.

The owner-only installer receives the exact synthetic catalogue and expected current version (`0` before the first installation). It locks the singleton pointer, validates the catalogue, installs its immutable original payload and derived rows, then advances the pointer in the same transaction. An empty location/amenity catalogue is valid and can be current. Listing saves compare the explicitly selected version with that pointer, rather than inferring currency from the highest existing location row.

Same-version identical payload replay returns the original installation without reactivating an older version. Changed payload at a retained version, stale expected current version and a new non-increasing version refuse. Failed validation or transaction rollback leaves the old pointer, manifest and reference rows intact. Runtime cannot invoke ingestion or write the pointer, catalogue or derived rows. The function uses the caller's migration-owner privileges; it does not grant a runtime principal owner authority.

SQL ingestion now independently checks exact field sets and synthetic policy/country, canonical positive safe version strings, canonical UUIDs, NFC and bounded canonical labels, globally distinct location/amenity IDs, distinct amenity codes, nonempty distinct applicable property types, and catalogue cardinality limits (5000 locations/100 amenities). Typed parent foreign keys and level constraints reject orphan, cyclic and wrong-level edges; a single multi-row insert permits valid child-before-parent input. Installed manifest and location/amenity rows reject UPDATE/DELETE. This remains a trusted migration-owner ingestion boundary: an owner capable of altering SQL objects is not an untrusted API caller.
