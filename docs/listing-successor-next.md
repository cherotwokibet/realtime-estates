# Successor listing revision: inspected implementation plan — 16 October 2026

Inspection of 0001_foundation.sql and 0002_listing_disclosure.sql confirms legacy save_draft/save_draft_v2 can allocate max(revision_no)+1 with expected revision version zero. They lock the listing but do not require the predecessor to be terminal, bind an expected listing version, retain an operation receipt, or increment listing version when allocating. The new workflow must not claim exclusive allocation while these entry points remain callable. Existing v1/v2 fixtures and old API callers require an explicit compatibility transition and denial tests before revocation.

Start with an immutable command containing operation UUID, listing UUID, expected listing version, predecessor revision number/version/state, and normalized full replacement private content. Only approved/rejected terminal predecessors qualify. Require the predecessor to be the current latest revision under the listing lock. A stale expected listing or predecessor version takes precedence over business-state refusals. Check revision-number/version exhaustion without overflow. Do not infer edit authority from a historical receipt.

Use explicit content supplied by the operator. For the first supported policy, the new revision starts with an empty gallery; do not copy accepted rows or public object keys across revisions. Existing accepted media is bound to revision-specific processing/attachment evidence. Any future reuse must establish a separate verified authorization and provenance contract. A convenience copy of text must be an explicit fresh authorized read and visible review, then frozen into the command; never implicitly fetch mutable content during retry.

An applied operation allocates predecessor+1 once, saves normalized content atomically, increments the listing version once, retains the initial successor revision version, and leaves predecessor content/review evidence and approved public snapshot unchanged. It cannot change availability, publication status, assignment, freshness or published revision. Permission/current tenant/current assignment checks apply before original receipt recovery. Original requester identity and exact command are required for replay; a completed result survives later edits but does not become a current version.

Migration 0023 should use immutable private request/result records with forced RLS and deferred completion linkage, following the verified creation reservation pattern. Under one transaction reserve operation, lock listing, lock/read latest predecessor, validate correlated versions/state, allocate/save or retain a bounded conflict/refusal result. Unknown failures roll everything back. Explicitly test wrong original actor, changed command, tenant/access loss/restoration, malformed input before mutation, later revisions, overflow, immutable rows/deferred orphan rejection, approved snapshot preservation and legacy bypass transition. Real PostgreSQL multi-connection races remain a separate hosted gate.

Then add fixed protected HTTP/SDK commands and original GET recovery, validate adapter receipts inside the transaction, and use one explicit browser write with retained original operation. Operator UI must block discard/replacement while uncertain, recover with GET, replay only deliberately, and open the successor editor through a fresh authorized read. Verify signed HTTP commit/reply loss and actual browser recovery, stale two-tab predecessor state, duplicate replay and unchanged public snapshot. Native devices/UAT/production release are separate tasks. No successor implementation or test pass is claimed by this plan.
