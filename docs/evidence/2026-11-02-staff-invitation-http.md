# Signed invitation HTTP and SDK — 2 November 2026, checkpoint269

The isolated single-use invitation engine now has shared strict contracts, a separately enabled HTTP adapter and five SDK methods. Actual local loopback Node HTTP + signed synthetic JWT/JWKS + isolated PostgreSQL tests connect issuance, original recovery, state, recipient acceptance and original redemption reads. This completes the transport slice; the admin BFF, retained issuance controller, one-time secret presentation and verified recipient UI are still unfinished.08-4 remains open;49/97(51%) and0/14 release gates are unchanged.

Commands retain operation and invitation identity only. Frozen detached validators reject getters, extra authority, malformed IDs, invalid dates/deadlines, noncanonical secrets and duplicate JSON. Raw secrets exist only in the explicit ephemeral issue response or redemption POST body. No new secret URL, browser persistence, delivery, email provider or ordinary error logging is introduced. The API returns metadata-only GET originals; replaying a committed issue returns secret:null without regenerating raw material or writing a new issue.

The new ApiServiceOptions.staffInvitationRedemption flag must supply the exact synthetic policy and trusted fixed verifier configuration. It is omitted from startup/preview bootstrap and normal migrations. Production and unknown modes are refused. The adapter uses configured company context and verifies signed issuer/audience/age/subject itself; the ordinary authorization hook cannot substitute recipient proof. Signed company/role claims do not grant authority. Each route validates the command/path identity, methods, query/fragment, cookie/conditional headers, application/json, fatal UTF8 and a2048-byte declared/actual handler body limit before SQL. The development HTTP bridge has its existing larger buffering bound; this is not a claim of a2048-byte socket allocation cap or hosted raw-target alias verification.

Successful wire responses require exact200 and Cache-Control:no-store. SDK methods omit browser credentials, forbid redirects, bound response bytes to8192, reject duplicate JSON and validate target-bound receipts. Network loss, timeout and malformed successful writes remain uncertain after a single POST. Recovery requires an explicit GET; there is no automatic write retry or replacement secret. SQL receipt validation still runs before commit and malformed issue/redemption receipts roll back all changes. Same redemption operation returns its historical receipt without reactivating a revoked member.
