## Read-only recovery feasibility findings

The v3 API already supports authenticated GET of reference creation/successor operations by listing and operation IDs. It reconstructs and validates original commands from the SQL receipt, historical catalogue and reference selection; the browser BFF currently requires the full original in a POST recovery body and the SDK validates against that original. An opaque ID-only recovery path can reuse this committed-operation read rather than add a second canonical receipt store. However, a never-received or still-in-flight write has no committed receipt yet: a404 lookup cannot establish a discarded outcome or authorize a new operation while the first can still arrive. Preserve the full original until a durable server-admission/sealed-envelope protocol covers that case. Existing synchronous session.retain/readback-before-dispatch guarantees must survive any async sealing migration. This is a source feasibility finding only, not an implemented or accepted recovery design.
