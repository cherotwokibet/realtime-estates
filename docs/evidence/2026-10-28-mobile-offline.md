# Mobile failure handling and client field capture — 28 October 2026

Checkpoint211. Independent synthetic implementation; no real account, prospect, stock, provider or vendor system changed.

The native reference catalogue now keeps at most one successful public response in memory for the exact normalized query and configured company/API session. If refreshing that same query fails within five minutes of the original load, the UI can show that previous response with an explicit UTC load timestamp, unverified counts/prices/availability warning, manual retry and clear controls. It does not infer that every failure is a network outage. It stores no catalogue response on disk, retries no request automatically and substitutes no demo stock. Paging is disabled while a previous response is displayed. Details can still be inspected as historical public information. Changing the query/page drops the buffer; clearing filters or the response invalidates it. This is short-lived session fallback, not an offline catalogue synchronization service.

Cancellation and newer requests invalidate late results. Caller query values are detached before I/O. Expired/backwards/invalid clocks, aborted requests and cleared/superseded work cannot refill the fallback. Existing SDK ten-second request timeout and bounded response validation remain. Search preferences keep their separate company/origin-scoped disk store and serialized writes; account credentials/private state are never put there.

The new negative test found an SDK defect: `attachRecord` assigned an own JSON `__proto__` field to an ordinary object, silently dropping/reinterpreting it before a caller's allowlist. It now defines every captured key as an own enumerable data property. Both ordinary and reference public searches reject string/null/object values for that unsupported field before network I/O. This fixes strict query validation; it is not evidence of account compromise or privilege escalation. No server authorization policy was weakened.
