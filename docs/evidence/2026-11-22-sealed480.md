It validates the original command before sealing and after authenticated opening. Wrong keys, tampered bytes/metadata, noncanonical base64url and oversized records fail closed. It follows the repository's existing first-party server-encryption pattern and [Node24 crypto documentation](https://nodejs.org/docs/latest-v24.x/api/crypto.html#ciphersetaadbuffer-options). Production and missing configuration stay closed. It asks the actual API for current verified staff leases before reading the body and again afterward. Only current admins whose tenant/actor match the captured scope may seal/open these two kinds. The browser client pins relative paths, omits credentials, refuses redirects/credential-bearing or altered response URLs, bounds JSON and validates scope/operation. The retained slot stores only an envelope, never the command or key. It waits for sealing and exact storage readback before returning, refuses replacement of a different outstanding original, serializes preparations and aborts pending/cached access on disposal or denial. A late uncooperative result cannot populate storage. No erase, replay, execution, successful-write or rollback API is exposed by this slot.

Sealing is stateless server encryption, NOT a durable server-side command admission or proof that an API mutation happened.
