The new proposal explicitly requires the existing branch, capture and membership candidates. It is absent from normal migrations, startup and preview bootstrap. Issuance stores only a SHA256 digest and immutable actor/issuer/capture/deadline metadata. One issue per capture and a unique digest prevent replacement regeneration. Original reads expose neither digest nor raw secret. Issuance preserves the captured deadline, checks current company/admin and exact active branch version after tenant-first locks, and uses the wall clock at decision time. Lost raw material requires explicit cancellation and a NEW capture/issue; existing originals remain immutable.

Redemption checks the trusted issuer, verified canonical email, subject, secret digest, current company, original inviting admin and exact active branch snapshot. Any existing company membership, including customer/inactive staff, is refused. It atomically inserts a new agent/admin membership, single-use consumption receipt and bounded audit. Replaying the same actor-bound operation returns historical metadata and never reactivates a subsequently revoked member. Another operation cannot consume the same invitation. Branch binding is recorded in the redemption receipt; no new branch-level authorization/filtering policy is claimed. The old capture receipt continues to report membershipGranted:false as historical capture evidence; a separate issued-state policy reports issued/used/revoked/expired. Consumed invitations cannot be falsely labelled revoked by the legacy cancellation writer. Legacy current-state/list routing still needs reconciliation before UI activation.

The server candidate captures fixed identity configuration and rejects production and missing/incorrect synthetic mode. Recipient email/subject/issuer come only from the existing signed fixed-issuer/JWKS/audience/age verifier with boolean email_verified. Request-supplied roles/email/actor are rejected. Current admin issuance still uses ordinary verified identity plus SQL authorization. Raw secret disclosure is explicit, one-time and only available after transaction success; ordinary result serialization contains no raw secret/digest. Explicit discard destroys retained material. Expected original absence uses a savepoint before the first write. A committed-reply loss destroys undisclosed material; subsequent recovery returns original metadata with secretAvailable:false and performs no replacement issuance write. Receipt validation happens inside the transaction, before commit. This object contract is not yet a public wire format; future HTTP must use host-resolved company context and bounded explicit response/secret handling.
