# Conservative listing duplicate hints

17 October 2026, checkpoint117. Migration0029 adds read-only `app_api.read_listing_duplicate_candidates(listing, listingVersion, revision, revisionVersion, limit)` to the reviewed local order. This is the SQL foundation of task06-6; no API, shared client or visible duplicate-review UI exists yet. The broad task stays open.

Current active admin membership in an enabled context company is required before lookup or stale-version disclosure. The target must exist in that company and its latest revision and listing versions must exactly match the request. The function compares the latest working revision of each other company listing, including non-public stock. It does not compare historical approved snapshots when newer working content exists. Candidate IDs, slugs, listing/revision versions, workflow state, availability and publication state are the only returned candidate fields. Private addresses, coordinates, contact details, prices and media references are excluded.

Policy `exact-current-work-v1` is a conservative engineering heuristic for human review: title and locality agree after POSIX whitespace collapse/trim and ASCII case folding; rent/sale purpose and property type agree exactly. Title must contain at least8 normalized characters, locality must be nonempty and purpose/type known. Missing facts return `insufficient_facts`, never a false assurance that no duplicate exists. Prices and bedroom counts do not establish identity and do not suppress hints when they differ. Punctuation, spelling, non-ASCII case/diacritics and semantic similarity are not folded. Different units in a building may match; differently described duplicates may not. No confidence percentage or claim of exhaustive real-world duplicate detection is made.

Results are ordered by listing UUID, with default20 and maximum25 candidates plus a lookahead `hasMore` flag. This bounds the response, not the database scan: the current query may examine company stock to obtain latest revisions. Hosted query-plan/load evidence and any measured index work remain open before production use. A no-match result means only no visible match under this exact current-work policy. The target and candidate facts can change after the statement; UI must request fresh detail before any later action.

There is no mutation, merge, deletion, archive, reservation or verification acknowledgement. The function does not create an audit event for a read. Future explicit verification decisions need their own permission/version checks and meaningful audit records. The private normalization helper has no runtime/PUBLIC execute grant; only the public admin-checked projection is granted to isolated API runtime. Media coordinator cannot call it.
