# Controlled local media maintenance

Checkpoint216 implementation,28–29October2026(EAT); local browser verification completed. Independently authored synthetic development composition only. No production sweeper, provider retention policy, multi-host process isolation or launch acceptance is implied. Vendor resources and the old live system remain available. ## Safe sequence

Use an original object returned by `createNativeMediaPreview` for its fresh owned root. Do not apply this procedure to vendor/customer/live directories, unknown or restarted roots, or a copied API object. The factory refuses production and occupied roots. Keep the maintenance database login separate from the API and processing logins, with only the reviewed NOINHERIT media_maintenance role. Obtain credentials through controlled server configuration, never a browser or logs.

1. Call `prepareNativeMediaMaintenance(nativePreview)`. It immediately fences new byte upload/finalize/image requests, then drains admitted work. It irreversibly retires the original Windows supervisor and waits for its owned job. Every unconfirmed outcome permanently withholds its same-instance opaque permit; no signal, process close event or historical journal is promoted into proof of termination. It also requires idle current worker admission and drains request/image/journal adapters. Null or an error means retain everything. The preview cannot resume ordinary byte operations after preparation.
2. With a non-null permit, use `MediaMaintenanceDatabase` bound to the trusted company to read a bounded candidate page (default25,maximum100). Its before-each-transaction guard refuses widened permissions and its two-second timeout bounds SQL work. No browser-selected company, actor, SQL, path or store is accepted.
3. For each candidate, use its retained original operation ID, or choose a new UUID once. Call `authorize(jobId,operationId)` and await a confirmed return. A lost COMMIT result is uncertain: stop without deleting bytes, then explicitly read candidates/recover the original ID. Never mint another ID as a retry. Every verified job and every attachment/intention reference is excluded, including removed or unattached verified output.
4. Call `retireNativeMediaJob(nativePreview,permit,authorization)` sequentially. The committed receipt must come from the restricted adapter, not arbitrary JSON. The factory checks company/capability identity, preflights the exact job workspace and delegates durable-store checks/fencing before unlinking. It removes only known unverified byte payloads and source.input/converted.webp/manifest.json files. Unknown entries, links, swapped ancestry or bounded-file violations retain resources. All receipts, journal facts and empty directories remain. No recursive deletion occurs.
5. Record the returned job/operation IDs and per-attempt removed-file/byte counts without image bytes, credentials or prospect information. An interrupted cleanup can be explicitly retried with the same original admission and live permit; a partial fence/integrity error requires investigation, not automatic repair. Counts are per attempt, never inferred cumulative totals or company totals. Page with the last observed job UUID, then restart from the beginning on a later run to catch newly expired lower UUIDs.
6. Close the preview after maintenance. Normal close also fences the supervisor and waits for maintenance/preparation before closing stores. It does not assert successful containment when an earlier outcome was unknown. Other preview/live resources are not closed or killed.

The authorization grace is one hour after the job's24-hour registration lifetime, and all processing leases end no later than job expiry. SQL admission is auditable immutable metadata, not a physical-cleanup completion claim. The durable expiry fence survives reopen and rejects late reads/installs for that job. Incomplete payloads without receipts can be removed after the same checks; verified media are always retained by this policy. Operator/provider retention, quotas, alerts, off-device recovery and release coordination still need their own acceptance evidence.

## User cancellation and readback

The photo uploader provides Cancel upload while its request is active. It aborts the owned browser request, preserves the original IDs and does not infer server rollback. The request timeout remains35seconds and no automatic retry is added. Completion removes the abort listener; unmount aborts owned work. If a response arrives after cancellation, the UI requires original-result readback before adopting it.

An original failed/timed-out/cancelled conversion may be described as native_failed only from a matching retained termination fact with a confirmed empty job. Request, claim, journal, attempt, lease nonce and working directory are bound to the original persisted request/current SQL lease. Unknown containment stays blocked. This is descriptive history, never a new launch permit, renewable lease, current global-capacity assertion or cleanup capability. A recorded successful exit without a sealed verified result is not converted into a failure or a success.

Before an attachment intent exists, the operator can explicitly leave a verified or no-longer-waiting uncertain upload unattached. It reads a fresh gallery and requires explicit adoption before continuing. It neither deletes nor resends anything; a late verification cannot attach an image automatically because no attachment intent was created. Unknown attachment operations remain locked for original-result recovery. This distinction permits cancel-before-admission recovery without falsely asserting that an upload never reached the server.
