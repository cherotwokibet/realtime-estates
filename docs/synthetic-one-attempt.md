# One explicit synthetic processing workflow — 11 October 2026

Stage06 work started: join the existing restricted SQL, durable byte store, persistent worker admission, attempt journal and Windows image supervisor in one reusable workflow. Synthetic local inputs only. Implemented and verified locally: 142 focused media tests and all eight workspace typechecks passed. See [executed evidence](evidence/2026-10-11-media-one-attempt.md).

The independently authored Node-only `@realtor/media/one-attempt` controller accepts trusted infrastructure configuration and one explicit `{jobId,claimId,generationId,input}` request. One controller admits one run; request history cannot restart it. Use the same configured worker/journal/store roots across controllers. The child receives fixed codec arguments and generated working files, without SQL credentials or account/actor selection.

Before capture/claim SQL, the workflow reserves the worker and persists the actual input together with its original generation, hash, byte length, generated private object IDs, claim, pipeline, store and worker/journal/reservation identities. The separate `processing-request` store permanently reserves the job and issues a same-instance one-use ticket. Reopening supplies facts only. A request that failed after reservation cannot be repaired, overwritten or replayed as new work.

Capture, claim and seal writes are each attempted at most once. Only a known uncertain COMMIT may trigger an exact read-only `readProcessing` comparison within that same live run. Missing, conflicting, inaccessible or superseded facts block; there is no generic write retry, newer lease adoption or revision-token substitution. A matching historical lease must still be unexpired before new native work. SQL exposes only the latest lease, so superseded original claims cannot be recovered through that projection.

The original live journal ticket must be consumed by successful worker arming before native launch. Unknown containment or an error after arming retains the attempt and worker slot. Proven empty failed/cancelled/timed-out work may release capacity without accepting output. Successful exit and actual zero-process accounting must precede independent bounded file readback, byte/hash/header/manifest verification and durable output installation. The exact full lease, output identity and seal manifest are persisted before the single seal write. PostgreSQL's manifest digest is compared as a returned database fact; it is not reproduced using JavaScript JSON serialization.

Explicit `reconcile(binding)` reads original request, byte and SQL history. It does not call upload eligibility, capture, claim, seal, reserve, arm, release, launch or cleanup. A matching sealed result can be reported after reopening, while still requiring its original stored seal request and matching durable bytes. Historical process observations never grant promotion or relaunch authority.

Trusted stable local filesystem and infrastructure configuration remain prerequisites. No scheduler, automatic resume/retry/reclaim, repair/delete, root rotation, sweep, production upload transport, accepted listing attachment, audit/retention/quotas or provider isolation is supplied. Local success does not prove hostile filesystem resistance, Windows ACL/network/CPU/memory isolation, power loss, worker/database crash recovery or independent PostgreSQL races.
