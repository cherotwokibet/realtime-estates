# Reference deployment admission foundation — checkpoint 174

25 October 2026. A trusted owner-side admission utility now refuses an application/configuration rollback that would strand adopted reference facts or historical originals. This is an independently implemented control-plane foundation, **not an installed production deployment gate**. No launcher, API startup, hosting setting or migration runner was changed to invoke it. `database/reference-deployment-admission.mjs` exports `withReferenceDeploymentAdmission(connection, capabilities, activate)`. Its caller must supply an exclusively leased owner connection outside an existing transaction and a trusted application activation callback. It has no HTTP endpoint, customer input, environment credentials, arbitrary file/SQL path or migration installer. Capabilities are seven exact versioned protocol identifiers or explicit null, with exact own enumerable data fields; getters, extra/sparse fields and aliases fail before SQL. The configuration is frozen before any await.

The utility checks owner authority, sets a two-second lock timeout and holds a SHARE fence on revisions and every installed reference catalogue/receipt/transition/approved table while it examines persisted occupancy and invokes the activation callback. READ COMMITTED is deliberate: rows committed while waiting for the fence must be visible after acquisition. A repeatable-read snapshot taken before that wait could miss adoption. Data-changing commands remain blocked by the table locks until activation settles or admission rolls back. The utility changes no listing, reference data, receipt, schema or grant.

An entirely ordinary schema is admitted with every capability disabled. An installed, catalogue-only candidate also does not invent adoption. Partial core schema fails closed. Any adopted revision or original requires the combined editor, exact revision reader and original draft recovery. Historical transitions/approved snapshots additionally require transition recovery; approved snapshots require public reference reading; creation and successor originals require their matching recovery. Required SQL routines must still exist and be executable by api_runtime. Admission returns only a frozen policy/adopted/required-capabilities summary; it returns no rows, IDs, addresses, credentials or receipts. It calls activation only after all checks and commits only after that callback settles. Errors roll back instead of invoking activation or modifying saved originals.

## Required composition before acceptance

The utility is not yet wired into a real deployment/configuration controller. A self-reported capability object is not artifact attestation. The controller must derive it from the exact reviewed target artifact, verify the actual maintained editor/API/BFF/reader/recovery routes and preserve their flags, drain old writers, serialize all owner schema/grant changes and hold the exclusive database lease until activation settles. Owner DDL outside that controlled deployment path is not prevented. This utility never authorizes destructive schema downgrade. SQL routine existence/grants are checked; function-body provenance still requires the retained source hashes and reviewed migration plan.

The callback switches an external application and is not transactionally atomic with PostgreSQL. If activation succeeds but COMMIT acknowledgement is lost, the caller must reconcile the actual active artifact and database state; this module does not automatically roll back the external switch or make blind retries safe. A production controller needs bounded cancellation/deadline, artifact identity, health checks, failure reconciliation and hosted lock/concurrency tests. PGlite's sequential test connection does not prove those properties. Keep reference proposals default-off until that composition and the actual browser editing/recovery journey pass.
