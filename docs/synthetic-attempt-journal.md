## Frozen journal contract

Node-only `@realtor/media/attempt-journal` accepts a dedicated durable-store instance and a separate trusted existing attemptParent. That store belongs exclusively to this journal; ordinary photo input/output objects use another store. Binding is exactly `{jobId,claimId,attempt,leaseNonce}`, with canonical UUIDs and attempt1–3. No browser filenames, paths, actor selectors, database credentials or executable selection are accepted.

`reserve(binding)` returns a frozen intent and a fresh opaque runtime ticket only after two exclusive permanent reservations and canonical intent readback. The journal first validates its store through targeted read, then exclusively creates the documented `<store>/objects/<jobId>` directory. Any existing directory, including empty/incomplete/historical, blocks permanently. It then exclusively creates `attemptParent/jobId`, installs the intent as a quarantine-kind journal record and verifies its bytes. This deliberate dependency on the documented store layout distinguishes a fresh reservation from an exact generic-store replay. Any failure retains reservations; no replay ticket is reconstructed, even if an old empty native attempt directory was later removed.

Intent canonical order is version1, journalId, jobId, claimId, attempt, leaseNonce, attemptDirectory. Intent and terminal payloads are each bounded to4096 UTF8 bytes before writing; intent bounds are checked before either reservation. Journal references bind objectId=claimId and generationId=leaseNonce, with quarantine for intent and output for terminal. No timestamp, PID or SQL expiry releases these slots. A job has one reservation across its later SQL attempts too.

The later worker-admission dependency adds synchronous `consumeLaunchTicket(ticket)`: a same-instance live ticket can be consumed once before launch. Copied/foreign/consumed/observed tickets fail, as do closed or busy journals. Consumption changes runtime authority only, creates no new ticket and never comes from inspection. The consumed ticket remains valid for exact terminal recording. A valid termination request marks the ticket observed before I/O, so it cannot later become launch authority even when recording fails. The shared worker controller consumes before committing its launch record; a consumption/persistence failure conservatively burns that slot. See synthetic-worker-admission.md.

`recordTermination(ticket,outcome)` accepts only a ticket minted by this live instance. Its stored attempt-directory identity is rechecked. The trusted caller supplies the actual native supervisor outcome; the journal does not independently authenticate an OS receipt. Exact strict outcomes are either job_empty with activeProcesses0 and the existing four nonunknown states, or containment_unknown/unconfirmed/cleanupAllowedfalse. Inputs are snapshotted before awaits. Terminal bytes contain the exact intent followed by outcome, written through the durable store. Identical terminal retries recover; changed observations conflict. An unknown observation cannot be overwritten by a later success.

`inspect(binding)` reads explicit bounded records only. Missing/incomplete or unknown observations remain blocked. Malformed/noncanonical/corrupt/mismatched records fail integrity checks. A valid empty-job terminal yields `termination_recorded`: a historical observation, never a launch ticket or permission to read/promote output or clean paths. Fresh inspection anchors current identities; it cannot reconstruct prior directory provenance. No global startup scan, scheduler, automatic resume/retry, overwrite, repair, delete or retention sweep exists.

Only one journal I/O operation is active, with BUSY for overlap. This is not a global worker-admission lock: future orchestration must enforce its own persistent block for unconfirmed jobs. close stops admission, drains active work and closes its dedicated store. Changing configured journal/store roots to evade unknown history is outside the contract.
