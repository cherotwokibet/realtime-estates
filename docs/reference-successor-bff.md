`createReferenceSuccessorClient` captures fixed instance/tenant/actor/listing scope and validates full commands and selected historical catalogue facts locally. Browser POST bodies contain only the retained command; no catalogue, bearer token or caller-granted authority is added. The catalogue argument may be the selected subset retained by the controller. Create and explicit recovery each make one same-origin browser request with credentials omitted, redirects rejected and no-store caching. It verifies exact loopback host, same origin, instance and browser scope guards. Server credentials stay in the existing server-only configuration. Current actor/tenant identity is fetched from the upstream session; caller scope headers are compared as stale-session guards and never forwarded as authority. The BFF fetches the immutable catalogue version selected by the command, validates route IDs and full successor facts, then uses the checkpoint159 SDK method.

Create dispatches exactly one upstream successor POST. Recovery dispatches exactly one body-free upstream original GET. Both also perform supporting session and catalogue GETs; recovery therefore has three upstream reads, not one total network request. Current role, membership, requester, assignment and catalogue authority remain upstream API/SQL responsibilities.

Canonical route/body rules reject unsupported methods, query/fragments, authority/cookie/conditional/framing headers, duplicate fields, oversized bodies and invalid predecessor facts. Browser request and error-body limits remain 131072 bytes; a successful composed original may use 262272 bytes with independently validated 131072-byte components. Stream parsing rejects malformed UTF-8, duplicate fields and invalid canonical integer tokens and cancels oversized bodies. Production/orphan flags or changed loopback scope fail before upstream I/O. Stale actor/company scope fails before catalogue or command dispatch.

Lost/altered successful replies and cancellation after write dispatch preserve submission uncertainty. A known refusal can remain non-uncertain. Recovery failure is never converted into a write and is not labelled as a newly uncertain mutation. No hidden retry or recovery is introduced. Combined with the controller, an uncertain result remains retained and restored locally without requests; only explicit recovery observes the original. The confirmed handoff still exposes identity only for a fresh current draft read.
