# Private Cloud Run API invocation

Checkpoint 454 implements the server transport locally. It does not deploy a service, grant IAM permissions or prove real Google identity. Project boniface-realtor-staging still has billing disabled.

For each web/admin Cloud Run deployment, configure the fixed server-side HOSTED_CUSTOMER_API_ORIGIN or HOSTED_STAFF_API_ORIGIN to the API's canonical HTTPS run.app service origin. Set HOSTED_API_INVOCATION_CONFIG to exactly:

    {"policy":"cloud-run-invocation-v1","audience":"https://synthetic-api-123456.africa-south1.run.app"}

This URL is synthetic, not an existing service. Use the actual canonical URL returned by the controlled Cloud Run deployment, without slash, path, query or port. This initial adapter deliberately supports no traffic tags, custom domains or custom audiences: target and audience must be identical. Cloud Run also issues older service-name/hash URLs; one or two DNS labels before run.app are accepted.

The runtime requires NODE_ENV=production, APP_ENV=staging, matching GOOGLE_CLOUD_PROJECT and K_SERVICE; service account credential files refuse. Firebase and database settings retain their own validation, including TLS verification. Never supply HOSTED_API_INVOCATION_CONFIG or service credentials to a client component, browser or mobile app. A run.app API target without explicit invocation configuration fails closed rather than silently sending only a user token. The existing separately configured HTTPS adapter for non-run.app hosts remains available; it does not claim Google IAM protection.

The Google auth library 11.3.4 is now an explicit pinned API dependency, already present transitively from the Cloud SQL connector. It lazily obtains an ID-token client through attached workload ADC. The library manages token expiry/refresh; concurrent requests share in-flight acquisition. Application HTTP requests use ordinary fetch exactly once, never Google client.fetch or its automatic retry behavior. Each request retains its own Firebase bearer token in Authorization and adds the Google workload token only in X-Serverless-Authorization. Tokens and provider diagnostics never enter returned error messages, HTML, browser storage or logs.

The transport fixes the API origin and supports only GET/POST under /v2/customer/ or /v2/staff/. It refuses caller-supplied workload credentials, cookies and actor/company/role headers, pins redirect=error, credentials=omit, cache=no-store and referrerPolicy=no-referrer, and refuses redirect/cross-origin responses. A five-second deadline bounds token acquisition and application response headers, with caller cancellation propagated. A late token cannot cause a cancelled request to send. Shared token retrieval may finish after a caller stops waiting; it cannot send that caller's application request. Existing SDK response-body deadlines and size checks remain responsible for response parsing. The transport never retries an uncertain write; the existing encrypted-original recovery protocol remains authoritative.

Browser customer/staff BFFs additionally reject incoming X-Serverless-Authorization before processing identity. The API container only forwards the ordinary Authorization header into Firebase verification and SQL membership policy. A Google service token never grants application user permissions. Conversely, a Firebase token is not a Cloud Run invoker credential.

Deployment requirements remain open: a dedicated service account for each web/admin service, roles/run.invoker granted on the target API only, authenticated invocation enabled on that API with no allUsers/allAuthenticatedUsers invoker grants, and reviewed ingress/VPC/egress paths. Cloud Run checks the service token at its managed boundary and removes its signature before the application sees it; the application does not treat that header as verified authority. Do not deploy the API as publicly invokable and assume this client header creates a private boundary. No IAM binding or ingress setting was changed by this checkpoint.

Local evidence uses injected Google token acquisition plus real loopback Node HTTP and disposable PGlite SQL, including lost customer/admin-branch acknowledgements without duplicate writes. Local production HTTP profiles verify configuration, SSR and origin refusal, not live authentication. Real Google ADC, invoker grants/denial, revoked identity, token refresh, private ingress and complete hosted browser/mobile/device/UAT acceptance still require evidence. Billing/spend, selected-region costs, migrations/role compatibility/retention and secret management remain separate open requirements. Keep the KES 10,000 baseline and existing vendor/live system.

Primary reference checked through native Firebase developer knowledge tools on 19 November 2026: [Cloud Run service-to-service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service). Installed google-auth-library ID-token source/types were inspected for cached token/header behavior; no long-lived service account key was created.
